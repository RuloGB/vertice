## Issues

### WARNING

1. Proposal Success Criterion 6 is textually overbroad and not literally true. It reads no
   frontend code matches on a ScanIssue.reason value, but isUnavailableRootWarning in
   scanDiagnostics.ts does exactly that (for the root-echo classification, not client detection).
   The design document is internally consistent and honest about this (explicitly calls it V5, a
   known load-bearing coupling, out of scope to remove), so this is not a hidden defect -- it is a
   loose sentence in the proposal that a future reader could misread as zero string matching
   anywhere. Recommend tightening the wording at archive time rather than blocking archive on it.

2. domain-model delta scenario ClientPresenceStatus is exhaustively matchable has no covering
   test. The scenario explicitly requires a match over every ClientPresenceStatus variant with no
   wildcard arm to compile, as the proof the enum is closed -- mirroring the existing
   scope_is_exhaustively_matchable_without_a_wildcard_arm pattern in model_contract.rs for Scope.
   Grepped the whole diff: resolve_bundled_slot decides the status via an if/else on a bool
   (any_candidate_root_exists), not an enum match, and no test anywhere performs an exhaustive
   match on ClientPresenceStatus. Practical risk is low -- the enum has no non_exhaustive
   attribute and derives Eq, so it is closed by construction regardless -- but per the skill own
   decision gate, a spec scenario is compliant only when a covering test passed at runtime, so
   this scenario is technically untested. A two-line test analogous to the Scope one would close
   this cheaply.
