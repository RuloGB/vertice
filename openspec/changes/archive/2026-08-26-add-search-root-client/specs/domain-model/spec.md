# Delta for Domain Model

## ADDED Requirements

### Requirement: SearchRoot Carries Its Owning Client

`SearchRoot` MUST carry `client: Option<ClientKind>`. Every client-specific
root MUST carry `Some` with its owning client. The shared `agents-skills` root
MUST carry `None`; `None` means shared ownership, not an unknown client.

#### Scenario: Client-specific root carries a typed owner

- GIVEN the fixture root `claude-skills`
- WHEN its `SearchRoot` is constructed
- THEN `client` is `Some(ClientKind::ClaudeCode)`

#### Scenario: Shared root carries no single owner

- GIVEN the fixture root `agents-skills`
- WHEN its `SearchRoot` is constructed
- THEN `client` is `None`
- AND the root remains a valid, reportable `SearchRoot`

### Requirement: Location Carries the Producing Root Client

`Location` MUST carry `client: Option<ClientKind>`, copied from the root that
produced it. This field MUST be typed ownership data, not a display label;
`None` MUST mean a shared root and MUST NOT be treated as an error.

#### Scenario: Fixture adapter preserves a client owner

- GIVEN a skill location produced from the `claude-skills` fixture root
- WHEN the location is inspected
- THEN `client` is `Some(ClientKind::ClaudeCode)`

#### Scenario: Fixture adapter preserves shared ownership

- GIVEN a location produced from the `agents-skills` fixture root
- WHEN the location is inspected
- THEN `client` is `None`

### Requirement: Location Client Has Referential Integrity

For every location in a scan report, `Location.client` MUST equal the
`client` value of the `SearchRoot` that produced it. Consolidation MUST NOT
change that value or infer it from a root id string.

#### Scenario: Complete fixture preserves root ownership

- GIVEN the versioned `complete` fixture report
- WHEN every location is matched to its producing root
- THEN each location's client equals that root's client

### Requirement: New Client Fields Generate TypeScript Bindings

The generated bindings MUST include both optional fields as nullable
`ClientKind` values, and MUST be regenerated by the Rust export tests rather
than hand-edited.

#### Scenario: SearchRoot binding exposes client

- GIVEN `SearchRoot.client: Option<ClientKind>`
- WHEN its binding is regenerated
- THEN `SearchRoot.ts` declares `client: ClientKind | null`

#### Scenario: Location binding exposes client

- GIVEN `Location.client: Option<ClientKind>`
- WHEN its binding is regenerated
- THEN `Location.ts` declares `client: ClientKind | null`

## MODIFIED Requirements

### Requirement: SearchRoot Distinguishes Absent From Present

`SearchRoot` (or an adjacent type it references) MUST be able to represent
that a root path was resolved and looked for on disk but does not exist,
distinguishable from a root that exists and produced zero components, and
from a root that exists and produced one or more components. This state MUST
be reportable by path alone. `SearchRoot` MUST NOT carry a client display name
or label; it MAY carry the typed `client: Option<ClientKind>` ownership field,
which is not stringly-typed presentation data.
(Previously: prohibited any client field while client identification was derived from `SearchRootKind`.)

#### Scenario: An absent root is representable without a display label

- GIVEN a root path that does not exist on disk
- WHEN a `SearchRoot` value is constructed for it
- THEN it is valid, reports that path as not found, and carries no client-name string

#### Scenario: Absent and present-and-empty are distinguishable values

- GIVEN one `SearchRoot` for a missing path and another for an existing empty path
- WHEN both are compared
- THEN they are unequal and preserve their own found/not-found state

#### Scenario: Existing fields and typed ownership coexist

- GIVEN a `SearchRoot` for an existing fixture root
- WHEN its `id`, `path`, `kind`, and `client` fields are inspected
- THEN the existing fields retain their prior values and types
- AND `client` is an `Option<ClientKind>`, never a display label
